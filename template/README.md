## Quick start

Use WSL/Linux as the primary development environment and keep the repository in
the Linux filesystem rather than under `/mnt/c`.

Copy the local configuration templates:

```bash
cp Environment.props.example Environment.props
cp .valheim/dev.json.example .valheim/dev.json
```

Then run a portable repository-only check:

```bash
./scripts/preflight.sh --portable
```

For full local validation after configuring a development Valheim installation:

```bash
./scripts/preflight.sh
./scripts/bootstrap.sh
```

See `docs/development.md` for local setup, server deployment, and
dependency/reference maintenance.

## Common commands

Validate project metadata:

```bash
python3 scripts/suite_metadata.py check
```

Synchronize supported metadata changes:

```bash
python3 scripts/suite_metadata.py sync
```

Run tests:

```bash
./scripts/test.sh
```

Build:

```bash
./scripts/build.sh Debug
```

Inspect the configured Valheim/Jötunn/BepInEx development stack:

```bash
python3 scripts/update-game-stack.py check
```

Refresh game references after a Valheim binary/reference update:

```bash
python3 scripts/update-game-stack.py refresh
```

Create deterministic Release packages:

```bash
./scripts/package.sh
```

See `docs/development.md`, `docs/dependencies.md`, and `docs/testing.md` for
details.

Server deployment is not tied to Docker. Local filesystem destinations and
remote POSIX or Windows servers over SSH are supported. Docker is an optional
lifecycle integration for restart, status, and log operations.

Managed hosts that expose only FTP/SFTP or a control-panel file manager require
manual deployment through the provider's tools because automated remote
deployment requires an SSH command channel.

Server deployment does not restart the server unless explicitly requested.

See `docs/development.md` for local and SSH deployment configuration,
transaction guarantees, and server lifecycle behavior.

## Metadata

`suite.config.json` is the editable source of truth for supported mutable
project metadata, including:

- version and publication metadata
- dependency pins
- project scopes and target frameworks
- client/server package membership

`suiteName` and `rootNamespace` are generation-time identity and are locked in
`suite.identity.lock.json`.

Use `scripts/suite_metadata.py` rather than hand-editing generated metadata
files.

## Licensing

HeimForge does not select a project-level license for generated repositories.

`LICENSES/MIT-0.txt` covers the HeimForge scaffold material. Before public
distribution:

1. choose a project license
2. add it as the root `LICENSE`
3. remove `LICENSE.todo`
4. run:

```bash
python3 scripts/suite_metadata.py check --release
```

See `docs/release.md` for the complete release checklist.
